# P32: truthful retained usage reporting

This local change is based on `739b2f0`. It does not deploy, activate publishing, change models, change paid-run cadence, add provider requests, or enforce a spending cap. Root owns integration with later source and graphics work. Regenerate the editorial-policy manifest after integration: `writer.py` is policy-bound and its existing response-capture blocks changed.

## Reporting contract

The existing `usd`, `calls`, `in`, `cached_in`, `cache_write`, and `out` values keep their historical meaning and cumulative MAX merge behavior. The price table is unchanged; its last documented check is 2026-07-13. This work did not independently refresh prices or reprice historical rows.

New writer responses add `priced_usd`, `priced_calls`, `unpriced_calls`, and `missing_usage_calls`. Known model prices and complete integer usage metadata yield a table estimate. An unknown model, missing metadata, or malformed quantities yield an explicitly unpriced response. An absent optional cache count can mean zero; an explicit boolean or empty string cannot. A returned response is not proof of a billed charge.

`known_cost_usd` is the subtotal of these priced estimates, not an invoice total. `legacy_estimate_usd` retains older estimates whose coverage is unknown. `recorded_estimate_usd` combines retained estimates where meaningful, with explicit coverage fields. Missing accounting, unknown-only rows, and legacy-zero-only rows return null for the recorded subtotal and projection. Legacy zero remains stored and exposed as a legacy estimate; it does not establish free usage. Inconsistent counters make the subtotal and coverage counts unknown. Valid legacy positive amounts remain visible without being promoted to verified accounting.

The Python reader, CLI status, actual authenticated dashboard API, and JavaScript reader share these meanings. The API keeps compatibility names `mtd_usd`, `projected_usd`, and `pct_of_budget`, now nullable and explicitly scoped to the recorded subtotal. No existing cost-chart component consumes those fields. The health page displays a neutral accounting note even when the budget reporting activity is idle. Missing or future dates cannot establish zero spending for those dates.

## Bounded merge evidence

New-coverage aggregates retain up to 32 original cumulative coverage tuples per day/model: `(calls, usd, priced_calls, unpriced_calls, missing_usage_calls, priced_usd)`. Numeric lexicographic ordering and equality avoid Python/JavaScript serialization differences such as 1 versus 1.0 and negative zero. Raw original coverage is checked before legacy normalization. Invalid evidence is sticky; sorted union retains the same smallest 32 witnesses regardless of grouping, and overflow is sticky and makes the subtotal unknown.

Readers check both original witnesses and pairwise MAX arithmetic. For example, two original one-response snapshots with different priced/unpriced classifications cannot become reassuring merely because a later snapshot has two calls. Generated MAX projections do not create new original witnesses. A drain adds one cumulative witness per touched day/model, not per individual response, and keeps its earlier evidence. The drain commits the copied ledger only after the complete fold succeeds; a failed fold re-buffers responses without partially modifying state or doubling earlier responses on retry.

The legacy money/token/call totals are not replaced by a per-call ledger. Two concurrent writers that each increment the same cumulative counters can still undercount. Witnesses expose detectable contradictions, not all concurrency, omitted responses, or omitted stages. Witness storage is bounded per existing day/model key; day retention remains 45 and the in-process response buffer remains 500. Neither model-key cardinality nor total account activity is newly bounded by this change.

## Threshold reporting and incident routing

The existing 70% and 90% thresholds still compare the recorded estimate subtotal to the configured monthly reference. Those rows remain degraded/failed. This is an alerting comparison, not enforcement; a small subtotal cannot establish that the complete account is below budget.

Below those thresholds or without a subtotal, API/CLI level is `coverage_incomplete`. The source-health row is a classified `skipped` row with `error_class=accounting_coverage`, not a new provider failure. The sentinel and dashboard treat that current reporting activity as idle immediately, even if the rolling history contains an earlier real threshold alarm. The displayed accounting note still states the limitation.

An existing real threshold issue remains untouched when the current accounting-only verdict cannot establish recovery. The sentinel neither files/reopens a new issue, adds repetitive comments, nor closes the old issue claiming recovery for this condition. Historical alarm rows remain unchanged. A later real threshold alarm retains the existing failure path.

The source sentinel itself exits zero. The existing workflow self-heal gate reads workflow conclusions, cadence and enabled status; this review established an incident-noise coupling, not a direct new paid-healer invocation from ledger coverage. No automation cadence or model configuration changed.
